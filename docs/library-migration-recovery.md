# Recovering a script from a mid-migration SRL-T/WaspLib install

This file documents a diagnostic and repair workflow for a specific, real failure class: the installed SRL-T/WaspLib source under `%LocalAppData%\Simba\Includes\` is internally inconsistent — some symbols were renamed, some weren't, and a script written against the "old" names won't compile. This is not a hypothetical pattern; it's what actually happened in this repository's research (see "Case study" below), and it is very likely to recur after any future SRL-T/WaspLib update that lands mid-refactor.

**When to reach for this file:** the compiler error is `Unknown declaration "X"` or `Duplicate declaration "X"` or `Type expected` in a file under `%LocalAppData%\Simba\Includes\SRL-T\` or `...\WaspLib\`, **not** in the user's own script — i.e. the failure is inside the library itself, not obviously caused by anything the script wrote. Also reach for §3.D/the case study's final rows if the failure is a **runtime** crash (not a compile error) pointing at a missing external file/URL that used to belong to this same broken ecosystem — the two failure classes share a root cause and turned up back-to-back in the same script.

## 1. Root cause (confirmed from direct source inspection + GitHub)

- Both `Torwent/SRL-T` and `Torwent/WaspLib` had their git history squashed to a single "Initial commit" on **2026-07-14**, with version numbers reset (SRL-T to `v0.1.0`, similarly for WaspLib) and a move toward a `WaspScripts` GitHub org. No tags predating that date survive on GitHub — the pre-reset source is not recoverable upstream.
- The **locally installed copy** (in this research: SRL-T 7.22.0, WaspLib 20.4.42) is the last pre-reset state, and that state was itself **mid-rename**: both `CHANGELOG.md` files show a burst of "more renames" commits in the days immediately before the reset (2026-07-05/07-06/07-08). The rename direction is consistently **dropping the `RS`/`ERS` prefix** (`TRSItem`→`TItem`, `TRSDoor`→`TDoor`, `ERSDoorType`→`EDoorType`, `RSTranslator`→`Translator`, `RSClient`→`GameClient`, `RSInterface`→`GameInterface`, `RSCacheParser`→`CacheParser`, etc.), alongside a parallel **structural split**: SRL-T now ships two parallel entrypoints, the legacy `osr.simba`/`osr/` tree and a new `main.simba`/`main/` tree; WaspLib mirrors this with its own `osr.simba` and `main.simba`.
- The rename was **not finished** before the reset. Some files (the shared `utils/` chain both entrypoints load) were already updated to the new names; the legacy `osr/` tree — which is what real, existing scripts are built against, including WaspLib's own shared `utils/` helper files — was not, and still references the old names.
- Whether this is connected to the wider July 2026 wave of OSRS bot-client shutdowns (PowBot, TRiBot, Storm Client, Inubot, OSMB all paused/closed within days of each other, per public reporting) is **plausible but not confirmed** — no source ties WaspScripts specifically to that event. Don't state it as fact; the squashed history and rebrand are confirmed, the cause of the reset is not.

## 2. Diagnostic workflow

For each `Unknown declaration "X"` error in a library file:

1. **Confirm X truly doesn't exist.** `grep -rn "X" <includes root>` for an actual `type`/`var` declaration, not just usages. Don't trust `search_lape_libs`/the generated symbol index here — it was built from a snapshot and may itself predate or postdate the rename; always re-check the live installed source (see `known-gaps.md`).
2. **Look for the renamed counterpart.** Strip a leading `RS`/`ERS` (or check the reverse — see below) and grep for that as a real declaration. This single heuristic resolved every case encountered so far:
   ```
   TRSItem -> TItem          ERSDoorType -> EDoorType
   TRSDoor -> TDoor          RSTranslator -> Translator
   RSClient -> GameClient    RSInterface -> GameInterface
   RSCacheParser -> CacheParser
   ```
3. **Determine which "side" is actually complete.** Sometimes the *old* name is the one with a full, working implementation and the *new* name is what's missing (e.g. `TWalkerV2` only exists in the new `main/` tree, which a legacy-tree script doesn't load — the fix aliases the new name backward to the already-loaded old `TRSWalkerV2`). Sometimes it's the reverse (`TItem`/`TItemArray` are the complete, current implementation; `TRSItem`/`TRSItemArray` are what's missing). Check both directions before deciding which way to alias.
4. **Don't reimplement from scratch if you can alias.** See §3 — reimplementing a type independently is fragile and was proven wrong mid-investigation (see the `TRSDoor` case study below).
5. **Once one symbol is fixed, proactively sweep for siblings** instead of waiting for the next one-off compile error. This works well:
   ```bash
   # every TRS*/ERS* identifier used in the reachable include tree
   grep -rhoE "\b(TRS|ERS)[A-Za-z0-9_]+\b" <legacy-tree-dirs> | sort -u > used.txt
   # every type actually declared anywhere in the installed source
   grep -rhoE "^\s*(T|E)[A-Za-z0-9_]+\s*=" <includes root> | sort -u > declared.txt
   comm -23 used.txt declared.txt   # dangling names
   ```
   Case-fold both sides (Lape is case-insensitive) to avoid missing matches on casing differences. Expect some noise (typos already present in the pre-reset source, doc-comment text, embedded binary data if you don't exclude `.zip`/`.png` files) — verify each hit against real usage before trusting it.

## 3. Fix patterns, and when to use each

**A. True type alias (`type NewName = OldName;` or the reverse) — the default.**
Use this whenever the dangling name is a *type*, not a variable. This is not a guess about Lape semantics — it's required by the actual shipped source: `SRL-T/osr/map/maploader.simba` assigns a `TRSDoor` value directly into `TWebGraphV2.Doors`, a field declared as `TDoorArray`, and assigns `ERSDoorType.WIDE` into a field typed `DoorType: EDoorType`. Neither compiles unless the old and new names are *literally the same type*, not just structurally similar. An earlier attempt in this investigation reimplemented `TRSItem`/`TRSTranslator` as independent types with hand-copied methods — that approach compiled at first but was abandoned once this cross-assignment requirement was discovered, in favor of aliasing. Prefer aliasing from the start.

Where to place the alias declaration matters, because `{$I}` in Lape/Simba is purely textual — there's no forward declaration. The alias must sit *after* whichever side already has a real definition, and *before* the first file that uses the dangling name. In practice this means editing the library's own entrypoint file (e.g. `SRL-T/osr.simba`) at a specific point in its include list — right after the `{$I}` line that pulls in the file defining the real type, and before the `{$I}` line for the file that needs the alias. Two insertion points were needed in this research: right after `{$I utils.simba}` (for names sourced from that shared chain), and at the very end of the file (for names only available once files loaded later in the same include list, like `osr/walker.simba`, have run).

**B. Direct call-site redirection instead of a variable alias — for live singletons.**
Some dangling names are *global variables* representing a stateful singleton, not types: `RSTranslator`/`Translator`, `RSClient`/`GameClient`, `RSInterface`/`GameInterface`, `RSCacheParser`/`CacheParser`. Lape has no variable-reference/alias mechanism (no confirmed `absolute`-style directive in this codebase — nothing in the installed source uses it, so don't assume it works), so a new variable of the aliased type is a *separate instance*, not the same object.
- If the singleton's state is static/deterministic (e.g. `Translator.Setup()` only ever assigns fixed constants — confirmed by reading its body), declaring a second variable and copying it once, right after the real one has initialized, is safe.
- If the singleton wraps something with real runtime identity — `RSClient.RemoteInput` is what `Mouse`/`Keyboard` actually attach to — a copy would silently create a second, disconnected `RemoteInput` instance. **Don't alias these; edit the handful of call sites directly** to reference the already-loaded old-tree singleton (e.g. `GameClient.RemoteInput.Setup()` → `RSClient.RemoteInput.Setup()`). This was correct in every singleton case encountered except the purely-static `Translator`.
- Check *every* occurrence of the dangling name in the file before considering it fixed — `grep -c` first. One round of this investigation missed two of three occurrences in the same file by only checking the first line reported by `grep -rln` (which lists matching *files*, not *lines*).

**C. Include-guard patch — for duplicate-declaration errors, not missing-symbol ones.**
A `Duplicate declaration "X"` error (as opposed to `Unknown declaration`) means a file got `{$I}`-included twice. In this case study it happened because WaspLib's shared `utils.simba` unconditionally cross-loads `SRL-T/main.simba` (guarded only by `{$DEFINE SRL_MAIN}`), and `main.simba` itself unconditionally re-includes `utils.simba` — colliding with a script that manually loads the legacy `SRL-T/osr.simba` first (which already included `utils.simba` once). Before patching, check what the redundant file *actually contains* beyond the duplicate include — if it's a parallel/equivalent implementation of something already loaded (confirmed here: `main.simba`'s own body is just the same `TSRL.Setup`/`TSRL.Debug` procedures `osr.simba` already provides), pre-defining its guard symbol (`{$DEFINE SRL_MAIN}`) to skip it entirely is safe. If it contains something genuinely unique, this approach will just surface those symbols as fresh `Unknown declaration` errors (pattern A or B) — which is what actually happened next (`TWalkerV2`, `GameClient`, `GameInterface`, etc. all turned out to be main-tree-only and needed backward-aliasing).

**D. Runtime asset fallback — a different failure class, not a rename.**
Not every post-migration failure is a dangling symbol. A script may have its own hardcoded download URL for a data file (e.g. `item-definitions.zip` from a `github.com/WaspScripts/wasp-assets` URL) that 404s because that repo no longer exists under either the org or the original author's account. Before disabling the feature, check whether the data was already cached locally by a prior successful run (`%LocalAppData%\Simba\Data\cache\...`) and whether the consuming code already has a graceful per-item fallback (it did here — `TItemData.GetDefinitions()` logs `Couldn't find X.json` and returns `nil` instead of crashing, for anything not already cached). If so, the fix is pointing the script at the existing cache directly and making the dead download non-fatal, not trying to resurrect the URL.

**This alone was not sufficient here, and the gap took several days of real runtime to surface** — worth internalizing as its own lesson, not just folded into pattern D above. Pointing `ITEMS_PATH` at the existing cache only helps for items *already in that cache*. The first time the script requested an item outside it, `TItemData.GetDefinitions()` fell through to `UnZipOneFile(Self.ITEMS_ZIP, ...)` — and `Self.ITEMS_ZIP` still pointed at the never-downloaded `item-definitions.zip`, which doesn't exist at all. That produced a **different failure mode than the one the surrounding code was written to handle**: `UnZipOneFile` (a compiled-plugin function, no readable Lape source) returns `False` gracefully when the zip *opens* but lacks the requested entry, but throws an *uncaught runtime error* when it can't open the archive file at all. The existing `if not UnZipOneFile(...) then DebugLn(...)` guard only catches the first case.

The general pattern worth remembering: **when a plugin-backed function takes a resource path/handle as an argument, "resource doesn't exist" and "resource exists but doesn't contain what I asked for" can be two entirely different failure modes** — one soft (return value), one hard (uncaught exception) — even though calling code often only guards for one of them. If you can't restore the real resource, and the consuming code already has a working graceful-degradation branch for "entry not found," redirecting into *that* branch by substituting a **minimal, valid instance of the same format** (here: a placeholder ZIP file, `scripts/empty-item-definitions.zip`) is simpler and safer than adding new error handling. Whatever code reads from that path then hits its own pre-existing "not found" path instead of a new one you'd have to write and verify yourself.

**A first attempt at this exact placeholder file failed and is worth recording as its own lesson.** The first version was a hand-written, byte-for-byte-minimal 22-byte "empty ZIP" — just a bare End-Of-Central-Directory record claiming zero entries, no actual local file header or central directory. It was verified by opening it with .NET's `[System.IO.Compression.ZipFile]::OpenRead` (via PowerShell), which accepted it fine and reported 0 entries. It still crashed the script with `Corrupt ZIP file` the next time it was exercised — because `UnZipOneFile`'s backend (an opaque Simba/plugin implementation, not the same code as .NET's zip reader) apparently doesn't accept a fully empty, zero-entry archive as valid, even though a well-known and widely-used zip reader does. **Verifying a workaround file against one library's parser is not the same as verifying it against the actual consuming code's parser** — when you can't inspect the real backend, prefer generating a *normal, complete* archive with genuine content (real local file header + file data + central directory + EOCD — e.g. via `Compress-Archive` with an actual placeholder file inside) over the most minimal technically-spec-compliant edge case you can construct by hand. Standard structure with real content exercises the common code path of virtually any zip reader; an empty/minimal archive exercises a rare edge case that's disproportionately likely to be handled inconsistently across implementations.

## 4. Case study: what was actually patched (this specific 7.22.0/20.4.42 install)

This table is a record of one concrete repair chain, not a general prescription — exact symbols, file paths, and the local cache hash will differ on another machine or after a library update. Kept here so a future session doesn't have to re-derive the reasoning from scratch if the same install is still in this state.

|---|---|---|---|

| `TRSDoor`, `TRSDoorArray`, `ERSDoorType` | type alias (old→new) | `= TDoor` / `= TDoorArray` / `= EDoorType` | same location |

## 5. Caveats

- These are **local patches to the installed library files**, not upstream fixes. They live outside this repository (`%LocalAppData%\Simba\Includes\...`) and are **lost on reinstall or update** — if SRL-T/WaspLib get reinstalled, expect to redo this workflow (though hopefully upstream will have finished the rename by then, making it unnecessary).
- The sweep in §2 step 5 only finds symbols actually *referenced* somewhere in the trees you scanned. It proved reliable across five rounds of "fix, sweep, run, hit a new one" in this research, but it is not a proof of completeness — a symbol only reached by a code path the script doesn't exercise (a rarely-used handler, an antiban task never triggered, etc.) will still surface as a fresh error the first time that path runs.
- **This applies just as much to runtime failures as compile-time ones, and takes longer to prove out.** The item-definitions fix looked complete after the script ran successfully once, but the actual gap (§3.D) only surfaced several real-world days later, the first time a specific, previously-unrequested item was looked up. A single successful run is not confirmation that a runtime-asset fix is complete — only that the code paths exercised *during that run* are fine. As of this writing the `empty-item-definitions.zip` fix has only been applied, not yet confirmed over an equivalent multi-day soak; update this note once it has (or once it hasn't).
- Verify by actually re-running the script after each batch of fixes. Don't assume a patch is correct just because it compiles — confirm the next error (if any) is a genuinely new symbol, not a sign the previous fix was wrong.
